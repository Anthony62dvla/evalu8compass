# How Well Are We Doing?

An Ofsted self-assessment tool for **maintained schools, academies and free schools, and independent schools**, across **EYFS, KS1–KS4 and post-16**, with an optional **specialist provision** layer.

It has two parts:

1. **Self-assessment checklist** (`index.html`): one person rates each expectation, and an AI education inspector suggests improvement activities and gives a readiness review.
2. **Staff workshop** (`workshop.html`): staff join on their own devices with a code, rate the school anonymously, see the collated findings broadcast back to them, and leaders turn the findings, the setting's context and the latest Ofsted report into an improvement plan.

---

## 1. Scope

### Users
- **Facilitator / headteacher**: runs workshops, agrees ratings, generates and shares the plan.
- **Staff**: teachers, TAs, support staff, senior leaders, governors. Join with a code, no account.
- **Leaders working alone**: use the self-assessment checklist.

### Features
| Area | Feature |
|---|---|
| Profile | School type, phases (EYFS–post-16), specialist provision. 117 criteria; each school sees 85–100, with wording and statutory references matched to its type |
| Checklist | Met / Partly / Not yet / N/A, evidence notes, progress, filters, AI suggestions per line, AI readiness review, action plan text, save/load |
| Workshop: join | 6-character code, `yourdomain/join/CODE` link and QR code. Staff pick a role only; no names |
| Workshop: respond | Staff rate lines (or "Don't know") and add comments; answers save automatically and can be changed until responses close |
| Workshop: collate | Live per-line results, staff score per area, role breakdowns, anonymous comments |
| Workshop: insight | **Staff split** flag (no clear majority) and **Leaders vs staff** gap flag (30+ point difference) |
| Workshop: broadcast | Facilitator shares findings to every staff device in one click; present mode for the projector |
| Workshop: agree | Facilitator records the agreed school rating and discussion note per line, or accepts the most common answers |
| Plan: context | Facilitator describes the setting (no personal data) |
| Plan: Ofsted report | Upload the PDF or paste the text; AI extracts grades, next steps, concerns and strengths, and maps each to checklist lines (shown on the findings) |
| Plan: themes | AI groups staff comments into themes |
| Plan: generate | AI writes 4–6 priorities with actions, leads, dates, evidence, success criteria and monitoring, tagged by source (agreed / staff / ofsted / context), plus quick wins and a message for staff |
| Plan: share | Facilitator shares a staff version of the plan to everyone's device |
| Export | Agreed ratings straight into the self-assessment checklist; full workshop record as JSON; plan as text |

### Privacy by design
- No names, emails or accounts for staff. Each device holds a random id and token.
- Role breakdowns and comment role labels only appear when **at least 3 people** in that role answered (`MIN_GROUP_SIZE`).
- Comments are shuffled so order doesn't reveal who wrote what.
- Exports contain collated findings only, never individual responses.
- Workshops are deleted after 90 days without activity (`SESSION_RETENTION_DAYS`).
- The staff comments and context are sent to the AI provider (Anthropic) when the facilitator uses the AI features. Tell staff not to include pupil names or personal details. Most schools should record this in their DPIA / privacy notice.

## 3. Running locally

Requires **Node.js 18+**. Nothing to install.

```bash
cp .env.example .env        # add ANTHROPIC_API_KEY (from console.anthropic.com)
npm start                   # http://localhost:3000  and  http://localhost:3000/workshop.html
npm test                    # simulated workshop: join, answer, collate, share, permissions
npm run check               # syntax + criteria validation
```

Without an API key everything works except the AI features, which explain how to switch them on.

## 4. Hosting on your domain

**Quickest route:** `bash deploy/install.sh review.yourdomain.co.uk --email you@school.org` on the server does everything below in one go. See `deploy/DEPLOY.md`.

Any server or VPS that runs Node 18+ works (e.g. a small DigitalOcean, Hetzner, Linode or Lightsail instance). Shared hosting that only serves PHP/static files will **not** run the workshop.

### Sharing a VPS with another project
This works well. The app uses about 50–100 MB of memory and very little processor time (the AI runs on Anthropic's side). Keep it separate from your other project:
- **Own port**: set `PORT=3100` (or any free port) in `.env`.
- **Not reachable directly**: keep `HOST=127.0.0.1` (the default) so only your web server can reach it. Check with `curl http://127.0.0.1:3100/api/health` on the server; from outside, the port should not answer.
- **Own subdomain**: add a new site block to your existing nginx/Caddy (below). Your other project's config is untouched.
- **Own service and user**: run it as its own systemd service, ideally under its own user, in its own folder.
- **Data location**: check your VPS is hosted in the UK or EU, and include `data/` in your backups.

Check Node with `node -v` (18 or later). If it's older and your other project needs that version, install a newer one alongside with `nvm` and point `ExecStart` at it.

### 4.1 Copy and start
```bash
# on the server
git clone <your repo> /opt/hwwd   # or upload the folder
cd /opt/hwwd
cp .env.example .env && nano .env # add the API key; set PORT=3100 and TRUST_PROXY=1
node server.js                    # check it starts, then Ctrl+C
```

### 4.2 Keep it running (systemd)
`/etc/systemd/system/hwwd.service`:
```ini
[Unit]
Description=How Well Are We Doing
After=network.target

[Service]
WorkingDirectory=/opt/hwwd
ExecStart=/usr/bin/node server.js
Restart=always
User=www-data
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```
```bash
sudo chown -R www-data /opt/hwwd/data   # create data/ first if needed
sudo systemctl enable --now hwwd
```
(pm2 works too: `pm2 start server.js --name hwwd`.)

### 4.3 HTTPS and your domain
Point a DNS A record (e.g. `review.yourdomain.co.uk`) at the server, then put a reverse proxy in front.

**Caddy** (simplest, automatic HTTPS), `/etc/caddy/Caddyfile`:
```
review.yourdomain.co.uk {
    reverse_proxy 127.0.0.1:3100 {
        flush_interval -1
    }
}
```

**nginx** (with certbot for HTTPS):
```nginx
server {
    server_name review.yourdomain.co.uk;
    client_max_body_size 25m;               # Ofsted report PDFs
    location / {
        proxy_pass http://127.0.0.1:3100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;                 # needed for live updates
        proxy_read_timeout 1h;
    }
}
```
Then `sudo certbot --nginx -d review.yourdomain.co.uk`.

**Cloudflare**: works with the proxy on. Live updates use Server-Sent Events, which Cloudflare passes through.

Staff then join at `review.yourdomain.co.uk/join/ABC123`, or by scanning the QR code on the facilitator's screen.

### 4.4 Hosting under a sub-path
If the app lives at `yourdomain.co.uk/review/`, proxy that path to the server with the prefix stripped. Join links then use `workshop.html?code=…` automatically.

### 4.5 Back-ups
Workshops are JSON files in `data/sessions/`. Back up that folder (a nightly `rsync` or your host's snapshots are enough).

### 4.6 Scaling note
One small server comfortably handles several simultaneous workshops of a few hundred staff. Running **more than one server instance** needs a shared database and message bus (replace `lib/store.js` and the SSE hub in `lib/workshop.js`, e.g. with Postgres + Redis or Supabase).

## 5. Running a workshop

1. **Before**: open `/workshop.html`, choose **Run a workshop**, enter the school details and pick 2–3 areas for a 30–40 minute session.
2. **Start**: project the dashboard (use **Present mode**). Staff join with the code or QR, pick their role and rate each line.
3. **Collate**: watch answers arrive. Use the **Splits and gaps** filter to find the conversations worth having.
4. **Broadcast**: tick **Share findings with staff**. Everyone sees the results on their device. Discuss the splits and gaps.
5. **Agree**: record the agreed rating and a note for each line (or **Agree most common answers**, then adjust).
6. **Close**: tick **Close responses**.
7. **Plan** (can be later, by the headteacher): add setting context, upload the latest Ofsted report, summarise comments, **Generate plan**, edit, then **Share plan with staff**.
8. **Keep**: Export → **Copy for checklist** to load the agreed ratings into the self-assessment, and keep the workshop record.

The facilitator's browser remembers the workshop. To hand over to the headteacher on another device, use **Copy facilitator link** (it gives full control, so share it privately).

## 6. Workshop API (for developers)

All under `/api/w`. Facilitator calls need header `x-facilitator-key` (or `?key=` on the events stream).

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/w` | anyone | Create `{ profile, areaIds }` → `{ code, key }` |
| GET | `/api/w/:code` | anyone | Workshop info and lines |
| POST | `/:code/join` | staff | `{ role }` → `{ pid, token }` |
| GET | `/:code/mine?pid&token` | staff | Own answers |
| PUT | `/:code/answer` | staff | `{ pid, token, itemId, s, c }` or `{ pid, token, answers: [...] }` |
| GET | `/:code/events` | both | Live stream: `state`, `results`, `plan` (staff) / `ai` (facilitator) |
| GET | `/:code/results` | facilitator, or staff once shared | Collated findings |
| POST | `/:code/control` | facilitator | `shareResults`, `sharePlan`, `status`, `agree`, `agreeAll`, `context` |
| POST | `/:code/report` | facilitator | `{ filename, pdf }` (data URL) or `{ text }` → AI reading |
| POST | `/:code/themes` | facilitator | AI comment themes |
| POST | `/:code/plan` | facilitator | AI improvement plan |
| GET | `/:code/export` | facilitator | Full record without keys or individual responses |

## 7. Customising

- **Criteria**: edit `public/js/criteria.js` (fields documented at the top), then `npm run check`.
- **AI behaviour**: edit `public/js/prompts.js`. If you change a JSON shape, update the matching render function (`adviceHTML`/`renderReview` in `app.js`, `reportHTML`/`themesHTML`/`planHTML` in `workshop.js`).
- **Branding**: teal brand tokens (`--brand-deep`, `--brand`, `--brand-bright`, `--brand-tint`) at the top of `public/css/styles.css`. Status colours (Met / Partly / Not yet) are deliberately different from the teal; keep them distinct if you change the brand.
- **School logo**: added in the app (checklist: "Add school logo"; workshop: when starting a workshop). PNG, JPG, WebP or SVG under 200 KB.
- **Icons**: Tabler Icons (MIT), bundled in `public/js/icons.js`, so nothing loads from outside at workshop time. To add one, put its name in `scripts/build-icons.js` and regenerate (instructions at the top of that file). Each evaluation area's icon is set by `icon:` in `criteria.js`.
- **Fonts**: Lexend (headings) and Public Sans (body) from Google Fonts, with system-font fallbacks. To avoid any outside requests, download them and serve from `public/`.
- **Anonymity threshold, limits, retention**: `.env`.

## 9. Keeping the content current

Criteria reflect Ofsted's renewed school inspection framework (from November 2025), the Education (Independent School Standards) Regulations 2014 and DfE statutory guidance (KCSIE, Working together to improve school attendance, RSHE, SEND Code of Practice, EYFS framework). Review `criteria.js` at least yearly, especially after KCSIE updates each September. AI output is advisory and never an Ofsted judgement.
